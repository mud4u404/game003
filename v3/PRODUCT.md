# v3 产品方向校准（2026-09-30；诊疗细节与美术待确认）

> 本文记录用户试玩《Project Hospital》后的纠偏。确认前不把具体 UI、美术或诊疗规则写成定稿。玩法参考不等于复制原作资产或病例数据。

## 用户明确的核心体验

医院按中国本土形象呈现，医生、护士和患者为中国人。玩家能够持续**看见**患者进入医院、候诊、依次进诊室，医生问诊、检查、推断、追加检查、诊断和治疗。常规患者由医生自动处理；玩家可以关注并接管病例，亲自选择检查、最终诊断和治疗方案。用户已确认这种“自动运行 + 自由介入”的操作边界。医院的专业人员、科室和检查能力应真实影响患者是否能获得及时、正确的诊疗。

玩家不以绘制墙体、调整门的朝向、逐件摆放家具为主要乐趣。建设应优先是按标准配置的科室/设施及其诊疗能力。移动端操作和信息呈现围绕追踪患者与诊断决策设计。

## 核对到的原作机制

开发商将建筑师、管理者、医生三种玩法并列；允许用预设医院快速进入医生工作，医生可以自动工作，玩家可介入复杂病例。官方介绍强调检查、化验与设备构成诊断谜题，Doctor Mode 允许接管医生并查看病例。开发者的医疗数据库教程表明：疾病由症状构成，检查揭示症状，治疗处理对应症状；检查还受房间、设备和人员能力限制。资料说明的是原作机制，并不是我们已经确定的具体数值实现。

## 建议的首个可玩验证（待确认）

从一座已经按标准配置好的中国医院开始。镜头能跟随一位患者经历：到院 → 候诊 → 进诊室 → 问诊与体格检查 → 列出有依据的疑似诊断 → 医生建议检查或玩家介入选择 → 患者实际前往检验/影像 → 结果返回 → 更新可能诊断 → 治疗/转诊/住院 → 离院。旁观时医院持续自动运行；玩家点开病例才展开诊断信息与干预选项。

首批病例必须有**信息逐步揭示和多种合理分支**，不能预先固定成 `诊室 → 检验 → 诊室` 的脚本。检查要有时间、费用和资源占用，并说明为什么有用；可用能力不足时，要看见等待、外送或转诊及其结果。医生自动诊疗有能力差异，但不应凭空知道隐藏病情。医学内容另行核验，不使用开发时随意编的诊断、检查或疗效参数作为正式内容。

## 用户补充确认：可追查、可改进的诊疗质量

同一疾病由不同水平的医生处理，判断、检查选择和治疗结果应可能不同；任何医生都不能保证永远准确。医院专业度也不是单个加成数字，而是可观察的科室、设备、人员协同和流程能力。一次延误或错误至少要能追查三类因素：

| 因素 | 游戏中可见的证据 | 玩家能做的调整 |
|---|---|---|
| 医生个人能力 | 病历中的问诊发现、鉴别诊断、检查选择、复核与治疗决策 | 培训、岗位调整、招聘或更换医生 |
| 医院设施和专业能力 | 检查是否可做、排队、报告质量、治疗资源是否到位 | 购置设备、增加相应岗位与科室 |
| 流程与协作 | 分诊、转诊、检查预约、报告回传和复诊的时间线 | 修订流程、排班和岗位协作 |

记录具体事件及时间，允许多种因素共同造成结果。玩家应从患者轨迹和病历调查原因，而不是被系统凭空告知“医生差”。改进后让后续同类患者出现可观察的差异；不能用简单的“治愈率 +10%”替代真实路径。病例结局必须与临床内容审校相符。

## 美术与审批节点

当前仅确认需要**重新选择**画面方向；此前的 v04 手绘等轴参考、白模和半写实探索都不自动成为 v3 定稿。先呈现同一个中国医院场景的可比美术方案（同一机位、同一患者流程节点、9:16），由用户确认后再做资产和界面。玩法循环、患者信息卡、场景美术、动态表现分别给用户看可审查样例，确认后再扩展。

## 现有代码的状态

`v3/src/hospital.js` 目前只验证网格占地、通路、人员设备缺失和按**预设路线**服务；这是上一轮搭的临时规则夹具，**不是**本草案的诊断引擎。它不能证明患者问诊、鉴别诊断、检查结果和治疗逻辑已实现。接下来的代码应按确认后的病例体验重新设计，不围绕门向与家具位置继续扩展。

## 仍需用户确认

1. 已确认：自动接诊为常态；玩家接管病例后可亲自选择检查、最终诊断和治疗。
2. 待确认：诊疗质量的首个病例切片与信息展示方式。
3. 待确认：三种同场景美术方向；选定后才固定风格并制作游戏资产。
