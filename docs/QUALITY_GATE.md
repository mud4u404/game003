# 交付前审查

此门槛由“患者不去看病”反馈触发。模拟测试通过不代表游戏可用，独立回放页能运行也不代表正常入口运行正常。基础接诊或存档问题未定位时，暂停新增玩法；不可把玩家当作首次验收人员。

## 三层证据

1. 规则和流程：运行 `npm run verify`。GitHub 的 `.github/workflows/quality.yml` 在 push/PR 时也执行这一层；它不会代替浏览器验收，是否要求分支保护由仓库设置决定。逐个患者检查是否持续推进，不能用总收入、总接诊人数掩盖个别患者永久滞留。包括无院内检查/药房的外部接续、采样、报告复核、药师审核发药、急症优先及恢复。每次修复补能发现同类问题的回归。
2. 正常游戏入口：用独立浏览器存储在 `/` 从选址、服务、招聘、复核走到开业。观察真实帧循环和时钟；确认登记、护理评估、医生叫号、完成接诊和离院。打开人物记录核对流程与画面。刷新后继续，既不重开首诊也不重复收费，检查控制台错误和画布更新时间。不得以独立夹具、修改患者状态或直接调用引擎代替这一项。
3. 玩家可理解性：在手机竖屏看场景。任何持续停留都要能看懂当前状态，点开能解释原因和下一步。区分静息、岗位排队、急救暂停、走路、检查回传与故障；排队不编造准确完成时间。检查物理就位、岗位占用、姓名/外形、触控与遮挡。不得只看 DOM 文本就宣称动画合格。

改变检查/药房流程时，还须在正常入口验证对应服务；长时间报告/随访可用引擎时钟验证，但交接必须注明哪些是模拟时间、哪些是真实浏览器观察。测试入口不得覆盖玩家存档，验收后关闭开发页，不新增玩家用不到的调试按钮。

## 阻止交付的情况

- 患者已满足服务条件、岗位空闲，却始终不被安排；患者没有正常离院或交接路径。
- 状态写着“自主运行”，时钟/画面实际已停；存在未解释的运行时错误。
- 刷新丢失方案或诊疗进展、重复扣款/结算；损坏档案被覆盖。
- 看见患者走进房间，却没有对应工作人员或服务；没有进入房间却已算服务完成。
- 长时间等待没有清楚的原因；用加快全局时间、随机走动或增造患者掩盖问题。

发现阻塞先保留证据：入口、版本、当前环节、可见患者状态、时间是否推进、是否能刷新续接。无法访问玩家的实际存档时必须明确说明，不将另一份测试档案的结果称为“玩家问题已修复”。

## 每次交接记录

`HANDOFF.md` 写清：本次影响的链路、复现条件、根因或尚未证实的假设、具体改动、自动检查命令与结果、正常入口观察到的阶段、未验证的阶段、截图位置、是否改动玩家档案。未验证项写“未验证”，不能自动算通过。代码修正可以保存接力，但基础阻塞未消除时不能宣布可以恢复新增功能。

该门槛不是零缺陷保证，也不能代替临床内容审校或玩法判断。五分钟静息等现有时间参数仍是原型规则；测试成立不等于体验合理或临床模型完整。
