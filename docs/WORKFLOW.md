# 协作流程：Claude 策划审查，ChatGPT 开发

更新日期：2026-09-28。用户决定：**Claude 负责策划、设计和审查，并把具体开发任务拆成任务单；ChatGPT（Codex）按任务单写代码。** 用户负责拍板和在两者之间传递任务。

## 分工

| 角色 | 负责 | 不做 |
|---|---|---|
| 用户（院长本人） | 确认方向、选择方案、把任务单交给 ChatGPT、决定合并 | — |
| Claude | 玩法与系统设计（`GAMEPLAY.md` 等），知识库规划，拆任务单（`tasks/`），审查 ChatGPT 的提交 | 不承担主要编码；只在审查需要时写小修正或示例 |
| ChatGPT | 按任务单实现代码、测试、截图，更新 `HANDOFF.md` 和任务单的执行记录 | 不擅自改设计决定、不扩大任务范围 |

## 分工细则（2026-09-28 用户要求：节省 Claude 的用量，统筹和审核必须由 Claude 负责）

**交给 ChatGPT 做**
- 全部编码、测试、截图和浏览器验收。
- 资料检索与知识库条目起草（附来源）。
- 按任务单写详细的实现方案、代码注释、`data/README.md` 这类说明文档。
- 维护 `HANDOFF.md`、`README.md` 的运行说明、`tasks/README.md` 的状态。
- **交付前先自查**：在 PR 正文里逐条对照任务单的验收标准，写明每条“已满足 / 未满足 / 未验证”，附截图路径和命令输出。自查写得清楚，Claude 就能只抽查重点。
- 发现小的设计缺口时，先提出建议方案（写在 PR 或执行记录里），由 Claude 决定。

**Claude 保留**
- 统筹：决定做什么、先后顺序、拆分任务单。任务单写目标、范围、验收标准，不写实现细节。
- 设计决定：`GAMEPLAY.md` 等设计文档的修改。
- 审核：每个 PR 必审。先看 ChatGPT 的自查，再运行测试、看截图、抽查关键代码；医学和运营内容逐条审。
- 合并前的最终结论，以及与用户沟通。

## 一个任务的流转

1. **Claude 写任务单**：`tasks/T###-简称.md`，写明目标、依据、范围（做 / 不做）、验收标准、交付方式。任务单状态为“待开发”。
2. **用户交给 ChatGPT**，可以直接这样说：
   > 阅读 AGENTS.md、docs/WORKFLOW.md 和 tasks/T001-iso-scene.md，按任务单完成开发。
3. **ChatGPT 开发**：
   - 从最新 `main` 建分支 `codex/T###-简称`；
   - 只做任务单范围内的事；
   - 运行任务单要求的检查，保存截图；
   - 在任务单末尾的“执行记录”里写：做了什么、运行了哪些命令和结果、没做到或没验证的部分、发现的设计问题；
   - 更新 `HANDOFF.md`，推送分支并开 PR 到 `main`（无法开 PR 时告诉用户分支名）。
4. **Claude 审查**：读 diff、运行检查、渲染或截图对比，把结论写成 PR 评论：**通过** / **需修改**（逐条列出）。需修改时回到第 3 步。任务完成合并后，审查结论汇总进任务单的“审查记录”。
5. **用户合并**：审查通过后由用户合并（或明确授权 Claude 合并）。任务单状态改为“已完成”。

## 自动通知与接力（2026-09-28）

用户要求双方做完后立即通知对方，尽量不靠用户转述。**GitHub 的 PR 是双方的沟通渠道。**

**任务分支和 PR 由 Claude 预先建好（从 T002 起）**
- Claude 发布任务时，先建好分支 `codex/T###-简称`，把任务单状态改为“开发中”作为第一个提交，开一个指向 `main` 的草稿 PR 并立即订阅。
- ChatGPT **不要自己新建分支**：`git fetch` 后切到这个已有分支继续开发，推送到同一分支。
- 每次推送都会触发 GitHub 自动测试，测试结果实时通知 Claude。

**ChatGPT → Claude**
- 完成后在这个 PR 上留言“完成，请审查”，并把草稿 PR 标记为可审查（做不到就只留言）。Claude 会立刻收到通知。
- PR 标题写任务编号，例如 `T002 知识库格式与首批病种`；正文写自查结果（见“分工细则”）。
- 如果 PR 不是 Claude 预先建的（例如 T001），ChatGPT 自己开 PR 后，Claude 要等定时检查才会发现，最长约 1 小时；这时请用户直接告诉 Claude。
- Claude 另设有定时检查作为保底。
- 修改完审查意见后，推送到同一个分支，并在 PR 上留言“已按审查意见修改”，逐条说明改了什么。

**Claude → ChatGPT**
- Claude 的审查结论以 PR 评论的形式发出，开头写 `@codex`，结论为“通过”或“需修改”，需修改时逐条列出。
- ChatGPT 每次开始工作前，先查看自己的 PR 上是否有 Claude 的新评论，有就先处理。
- 如果 ChatGPT 在 ChatGPT Codex 云端连接了这个 GitHub 仓库，PR 评论里的 `@codex` 可以直接触发它开始修改，整个循环不需要用户转述。在本机运行时，需要用户对它说一句“看一下 PR 上 Claude 的审查意见”。

**本机接力脚本 `tools/codex-relay.mjs`（让本机的 ChatGPT 也能自动接手）**
- 在用户电脑上后台运行，每分钟查看 GitHub 上带 `<!-- relay:codex -->` 标记、由允许的账号发出的新评论（Claude 的任务或审查意见都带这个标记）。
- 发现后在本机调用 Codex CLI（默认 `codex exec --full-auto`）处理：切到对应分支、完成要求、推送。处理结束后脚本在同一个 PR 上留言附上结果，Claude 立即收到通知。
- 一次只处理一条，按顺序排队；状态和日志在 `tools/.relay/`（已加入 `.gitignore`）。
- 启动：`node tools/codex-relay.mjs`。可选环境变量：`CODEX_CMD`（Codex 命令，推送需要网络权限时在这里调整）、`RELAY_INTERVAL_SEC`（默认 60）、`RELAY_AUTHORS`（允许的发送账号，默认仓库所有者）。
- 首次使用由 ChatGPT 在本机验证：Codex CLI 的非交互参数、沙箱内能否 `git push`、`gh` 是否已登录，并设置为开机自动运行。验证结果写进 `HANDOFF.md`。
- 这样整个循环不需要用户转述：Claude 发任务或审查 → 脚本唤醒 ChatGPT → ChatGPT 推送并留言 → Claude 立即审查。

**审查通过后**：Claude 在 PR 评论里写明“通过，可以合并”，并通知用户。用户合并后，Claude 发布下一张任务单。

## 规则

- 设计以 `GAMEPLAY.md` 为准。ChatGPT 发现设计缺口或矛盾时，写在执行记录的“问题与建议”里，由 Claude 和用户决定，不自行改设计文档的决定。
- 任务单里没写的功能不做；做不完的部分如实标“未完成”，不宣称通过。
- 新代码在 `v2/` 目录重做（用户已同意重做）。旧原型（根目录 `index.html`、`src/`、`tests/`）保留不动，直到任务单明确要求替换或删除。
- 不引入第三方依赖和构建工具，除非任务单允许。
- 交付门槛沿用 `docs/QUALITY_GATE.md` 的三层要求：自动检查、在正常入口实际运行、玩家可理解性。旧原型专用的检查项（选址、开业等）只适用于旧代码。
